# Research — Major-company nonstandard careers surfaces for aplyx

## Summary
The best near-term expansion targets are not more browser scraping: prioritize deterministic adapters for Microsoft/Eightfold PCSX, Apple, Stripe, and additional Oracle Recruiting Cloud tenants, while treating Meta and Google as higher-maintenance custom surfaces — https://apply.careers.microsoft.com/api/pcsx/search?domain=microsoft.com&query=intern&location=&filter_employment_type=Internship, https://jobs.apple.com/en-us/search?search=software%20engineer&location=united-states-USA, https://stripe.com/jobs/search?query=software, https://eeho.fa.us2.oraclecloud.com/hcmRestApi/resources/latest/recruitingCEJobRequisitions?onlyData=true&expand=requisitionList.secondaryLocations,requisitionList.workLocation&finder=findReqs;siteNumber=CX_45001,limit=5,offset=0,sortBy=POSTING_DATES_DESC&limit=5&offset=0, https://www.google.com/about/careers/applications/jobs/results/, https://www.metacareers.com/graphql. Major employers often brand their own careers pages while still exposing usable ATS-backed feeds underneath: Datadog resolves to Greenhouse, Palantir to Lever, OpenAI to Ashby, Salesforce/Nvidia to Workday, American Express to Oracle Recruiting Cloud, and Microsoft to an Eightfold/PCSX API — https://boards-api.greenhouse.io/v1/boards/datadog/jobs?content=true, https://api.lever.co/v0/postings/palantir?mode=json, https://openai.com/careers/search/, https://salesforce.wd12.myworkdayjobs.com/wday/cxs/salesforce/External_Career_Site/jobs, https://nvidia.wd5.myworkdayjobs.com/wday/cxs/nvidia/NVIDIAExternalCareerSite/jobs, https://www.americanexpress.com/en-us/careers/, https://apply.careers.microsoft.com/api/pcsx/search?domain=microsoft.com&query=intern&location=&filter_employment_type=Internship.

## Approaches / Subtopics
### Public single-company JSON APIs: Amazon and Microsoft PCSX/Eightfold
- Amazon exposes an unauthenticated paginated JSON list at `www.amazon.jobs/en/search.json`; the response is large and contains fields sufficient for deterministic list ingestion, including job IDs, locations, dates, and description-like content — https://www.amazon.jobs/en/search.json?offset=0&result_limit=10&sort=relevant&country%5B%5D=USA.
- Amazon is a fully custom/internal company careers system rather than a multi-tenant ATS board; the practical fetch path is GET JSON with `offset`, `result_limit`, and filters, and this is stable enough to keep as a first-class source because it does not require browser state or a changing frontend token — https://www.amazon.jobs/en/search.json?offset=0&result_limit=10&sort=relevant&country%5B%5D=USA.
- Microsoft’s current public search surface is Eightfold/PCSX-shaped: its HTML includes Eightfold assets, `_EF_GROUP_ID = "microsoft.com"`, and the page endpoint metadata names `get_html_smartapply_matches_v2` — https://jobs.careers.microsoft.com/global/en/search?q=software.
- Microsoft exposes a clean JSON search API at `apply.careers.microsoft.com/api/pcsx/search`; the response contains `positions[]`, `displayJobId`, `name`, `locations`, `postedTs`, `creationTs`, `department`, `atsJobId`, and `positionUrl`, so list ingestion can be deterministic without Playwright — https://apply.careers.microsoft.com/api/pcsx/search?domain=microsoft.com&query=intern&location=&filter_employment_type=Internship.
- Microsoft’s list API does not by itself prove that full JD text is available in the same response; the public detail page renders a large Eightfold/PCSX HTML payload, so JD enrichment likely needs either a detail-page parser or discovery of a separate internal detail API — https://jobs.careers.microsoft.com/global/en/job/1970393556911730, https://apply.careers.microsoft.com/api/pcsx/search?domain=microsoft.com&query=intern&location=&filter_employment_type=Internship.
- Microsoft is worth targeting before Meta/Google because its current public API returns named JSON fields and does not require a persisted GraphQL doc ID, while Meta examples depend on changing `doc_id` values — https://apply.careers.microsoft.com/api/pcsx/search?domain=microsoft.com&query=intern&location=&filter_employment_type=Internship, https://github.com/nadavzhr/arachne/blob/008698584c97120c13c7e02f501f8ecfb33c286f/src/arachne/spiders/meta/spider.py.

### Oracle Recruiting Cloud / Fusion HCM: Oracle and American Express
- Oracle Recruiting Cloud exposes public Fusion HCM REST resources such as `recruitingCEJobRequisitions`; Oracle’s own configured tenant returns `TotalJobsCount`, `requisitionList[]`, `Id`, `Title`, `PostedDate`, location fields, facets, and null JD-detail fields in the list response — https://eeho.fa.us2.oraclecloud.com/hcmRestApi/resources/latest/recruitingCEJobRequisitions?onlyData=true&expand=requisitionList.secondaryLocations,requisitionList.workLocation&finder=findReqs;siteNumber=CX_45001,limit=5,offset=0,sortBy=POSTING_DATES_DESC&limit=5&offset=0.
- Oracle Recruiting Cloud list ingestion is deterministic but requires lazy JD enrichment because the list response returns `ExternalQualificationsStr` and `ExternalResponsibilitiesStr` as null for Oracle’s own tenant — https://eeho.fa.us2.oraclecloud.com/hcmRestApi/resources/latest/recruitingCEJobRequisitions?onlyData=true&expand=requisitionList.secondaryLocations,requisitionList.workLocation&finder=findReqs;siteNumber=CX_45001,limit=5,offset=0,sortBy=POSTING_DATES_DESC&limit=5&offset=0.
- American Express no longer appears to be an Eightfold target in the current public path; its official careers page links “Jobs” to `careers.americanexpress.com/en/sites/CX_1/jobs`, which is the Oracle Candidate Experience URL shape — https://www.americanexpress.com/en-us/careers/, https://careers.americanexpress.com/en/sites/CX_1/jobs?keyword=Software.
- American Express is therefore best handled as another Oracle Recruiting Cloud tenant-discovery problem, not as a bespoke Amex adapter, although the exact REST host/site combination still needs browser-network verification because the public branded page does not expose the REST URL in static HTML — https://www.americanexpress.com/en-us/careers/, https://careers.americanexpress.com/en/sites/CX_1/jobs?keyword=Software.
- Oracle Recruiting Cloud is worth continuing to generalize because community scrapers show the same `recruitingCEJobRequisitions` plus `finder=findReqs;siteNumber=...` pattern across JPMorgan, Nokia, Dell, BNY, and other employers — https://github.com/angelplusultra/job-shell/blob/ce120c699bbb80029667f8a5c170f764258e1e94/src/scrapers/chase/scraper.rs, https://github.com/kbhujbal/go-get-jobs/blob/f07b7a36f4301d27867d9f8622ce8319cd5f038a/sites/nokia.go, https://github.com/peviitor-ro/based_scraper_py/blob/c8a04363d835e1c77e37859d4648ede04936ba33/sites/dell.py.

### Workday CXS behind branded pages: Salesforce, Nvidia, Netflix-class employers
- Salesforce uses Workday CXS rather than a fully custom job board; the practical fetch path is POST JSON to `salesforce.wd12.myworkdayjobs.com/wday/cxs/salesforce/External_Career_Site/jobs` with `appliedFacets`, `limit`, `offset`, and `searchText`, and live POST returned a `total` plus `jobPostings[]` with titles and `externalPath` — https://salesforce.wd12.myworkdayjobs.com/wday/cxs/salesforce/External_Career_Site/jobs.
- Nvidia uses the same Workday CXS pattern at `nvidia.wd5.myworkdayjobs.com/wday/cxs/nvidia/NVIDIAExternalCareerSite/jobs`, and live POST returned a `total` plus `jobPostings[]` for software-related roles — https://nvidia.wd5.myworkdayjobs.com/wday/cxs/nvidia/NVIDIAExternalCareerSite/jobs.
- Salesforce and Nvidia are lightly branded Workday tenants rather than custom systems, so aplyx should treat them as tenant config additions to the existing Workday helper, not as new adapters — https://salesforce.wd12.myworkdayjobs.com/wday/cxs/salesforce/External_Career_Site/jobs, https://nvidia.wd5.myworkdayjobs.com/wday/cxs/nvidia/NVIDIAExternalCareerSite/jobs.
- Workday CXS ingestion is stable enough for deterministic review-only ingestion because the API shape is typed and tenantized, but the maintenance burden is tenant discovery and per-tenant facet differences rather than parser churn — https://github.com/kbhujbal/go-get-jobs/blob/f07b7a36f4301d27867d9f8622ce8319cd5f038a/workday/salesForce.go, https://github.com/raiigauravv/AutoApply/blob/e3733acb6eab48de3e72aa2b7b1566faf933d6c8/routes/scan.js.

### Standard ATS behind custom marketing pages: Datadog, Palantir, OpenAI, high-signal startups
- Datadog’s public careers site is custom-branded and its `/all-jobs/` page renders an empty filter shell in static HTML, but the underlying jobs are available through the Greenhouse board API under the `datadog` slug — https://careers.datadoghq.com/all-jobs/, https://boards-api.greenhouse.io/v1/boards/datadog/jobs?content=true.
- Datadog should not be a custom adapter; adding or ensuring the Greenhouse slug `datadog` gives deterministic ingestion with full Greenhouse content and less maintenance than parsing Datadog’s custom frontend — https://boards-api.greenhouse.io/v1/boards/datadog/jobs?content=true.
- Palantir’s public career links and community internship trackers resolve to Lever job URLs under `jobs.lever.co/palantir`, so Palantir belongs in the existing Lever slug path — https://github.com/ReaVNaiL/New-Grad-2024/blob/af15e2172ed72423a7423d6dcd6a811efeec955f/README.md, https://api.lever.co/v0/postings/palantir?mode=json.
- OpenAI’s branded careers search renders many roles while linking `Apply now` to `jobs.ashbyhq.com/openai/.../application`, so OpenAI belongs in the existing Ashby slug path despite its custom marketing page — https://openai.com/careers/search/.
- This class is high-yield but low-novelty: the right improvement is aggressive discovery of Greenhouse/Lever/Ashby slugs from branded pages and job links, not new scrapers — https://careers.datadoghq.com/all-jobs/, https://boards-api.greenhouse.io/v1/boards/datadog/jobs?content=true, https://api.lever.co/v0/postings/palantir?mode=json, https://openai.com/careers/search/.

### Server-rendered branded HTML: Apple and Stripe
- Apple’s search page renders job cards in static HTML with role title, team, posting date, locations, role number, weekly hours, summaries, and detail links; the practical deterministic path can be HTML extraction from `jobs.apple.com/en-us/search` query URLs — https://jobs.apple.com/en-us/search?search=software%20engineer&location=united-states-USA.
- Apple community adapters commonly reference `https://jobs.apple.com/api/role/search` as a POST API returning `totalRecords` and `searchResults`, but this endpoint returned 404 in live direct testing from this environment while the public HTML search page worked, so the lower-risk first implementation is HTML parsing with the API as an optional probe — https://github.com/dipak-bhujbal/career-jump/blob/695f1c46acfad615e383168d06711378b9d70659/services/api/src/ats/custom/apple.ts, https://jobs.apple.com/en-us/search?search=software%20engineer&location=united-states-USA.
- Stripe’s jobs search page renders role, team, location, and detail links in static HTML at `stripe.com/jobs/search`, so a deterministic HTML adapter can extract list items without browser execution — https://stripe.com/jobs/search?query=software&office_locations=North%20America--United%20States.
- Stripe’s postings appear under stable `/jobs/listing/<slug>/<id>` URLs and duplicate a single job across multiple locations in the list, so ingestion needs de-duplication by listing ID plus expanded locations — https://stripe.com/jobs/search?query=software&office_locations=North%20America--United%20States.
- Apple and Stripe are worth targeting because the rendered pages expose current jobs directly, but their maintenance burden is CSS/HTML template drift rather than API contract drift — https://jobs.apple.com/en-us/search?search=software%20engineer&location=united-states-USA, https://stripe.com/jobs/search?query=software&office_locations=North%20America--United%20States.

### Google Careers: high-value but brittle internal format
- Google Careers renders a public job-search page with total count, pagination, job cards, job IDs in result URLs, locations, experience labels, minimum qualifications, and “Showing 1 to 20” navigation — https://www.google.com/about/careers/applications/jobs/results/.
- The practical no-browser fetch path visible from the public page is HTML/embedded-data extraction rather than a clean public REST or GraphQL API, and the result URLs are stable-looking `/jobs/results/<numeric-id>-<slug>` links — https://www.google.com/about/careers/applications/jobs/results/.
- Google is not as stable as Amazon or Microsoft PCSX for deterministic ingestion because prior local investigation found the raw source to be a Google internal Boq/`AF_initDataCallback` embedded-data format with positional arrays rather than named JSON fields, while the public rendered page still proves jobs are visible on first-party Google Careers — https://www.google.com/about/careers/applications/jobs/results/.
- Google should be considered only if coverage value outweighs parser fragility or if aplyx accepts a Playwright/search-page extraction path similar to LinkedIn/Indeed rather than a pure API source — https://www.google.com/about/careers/applications/jobs/results/.

### Meta Careers: GraphQL exists, but doc IDs and request context are fragile
- Meta Careers’ public site is commonly scraped through `POST https://www.metacareers.com/graphql` with a Relay persisted-query `doc_id` and `search_input` variables — https://github.com/nadavzhr/arachne/blob/008698584c97120c13c7e02f501f8ecfb33c286f/src/arachne/spiders/meta/spider.py, https://github.com/Myselfgitcone/job-hunter/blob/1229877a31e204437c3d4282e14711a0f30f23f8/backend/scrapers/meta_jobs.py.
- Meta’s maintenance risk is high because public examples show many different `doc_id` values over time, including `8807708415952871`, `9114524511922157`, `29615178951461218`, `27506805582236862`, and other values — https://github.com/Myselfgitcone/job-hunter/blob/1229877a31e204437c3d4282e14711a0f30f23f8/backend/scrapers/meta_jobs.py, https://github.com/nadavzhr/arachne/blob/008698584c97120c13c7e02f501f8ecfb33c286f/src/arachne/spiders/meta/spider.py, https://github.com/umutyesildal/daily-berlin-jobs/blob/0eaad4a8fdb302d674a82abbd29a305b9cc4251e/src/daily_jobs/scrapers/undone/meta_scraper.py.
- Meta is a fully custom/internal GraphQL surface, not a standard ATS, and direct POSTs may require browser-derived request fields or tokens because one community source explicitly marks direct native calls as `400 Bad Request` while Playwright-rendered access works — https://github.com/ragesh28/ALL_CAREER/blob/c56e2ae6fd174d02a064ede164c38e241051843d/job_api_calls.md.
- Meta is valuable but should be behind an adapter health check and fast failure path, because doc-ID refresh and request-shape changes are recurring maintenance costs — https://github.com/nadavzhr/arachne/blob/008698584c97120c13c7e02f501f8ecfb33c286f/src/arachne/spiders/meta/spider.py, https://github.com/ragesh28/ALL_CAREER/blob/c56e2ae6fd174d02a064ede164c38e241051843d/job_api_calls.md.

### Blocked or higher-friction custom surfaces: Tesla and TikTok-class employers
- Tesla’s careers search returned HTTP 403 to this read-only fetch path, so it is not a good first deterministic target without a browser/proxy strategy and ToS/rate-limit review — https://www.tesla.com/careers/search/?query=software&site=US.
- TikTok/ByteDance roles often appear behind custom `lifeattiktok.com` or `careers.tiktok.com` position URLs in internship trackers, but this research did not verify a stable public JSON API for that class — https://github.com/vanshb03/Summer2027-Internships/blob/3b6ec4a7aa7660b2ee5ca7db7670fb584c8de6d3/OFFSEASON_README.md.
- These blocked/high-friction sources should follow after Microsoft PCSX, Apple, Stripe, and tenant expansion because they need more browser/network work and have more anti-automation risk — https://www.tesla.com/careers/search/?query=software&site=US, https://github.com/vanshb03/Summer2027-Internships/blob/3b6ec4a7aa7660b2ee5ca7db7670fb584c8de6d3/OFFSEASON_README.md.

## Conflicts
- Microsoft older community scrapers use `gcsservices.careers.microsoft.com/search/api/v1/search`, but the current official Microsoft careers page is Eightfold/PCSX-flavored and the currently working public JSON surface is `apply.careers.microsoft.com/api/pcsx/search` — https://github.com/DandaAkhilReddy/agentchainswebsite/blob/89597c11901838079f33ee4d6207d0292b8c1684/api/src/lib/msCareers.ts vs https://jobs.careers.microsoft.com/global/en/search?q=software and https://apply.careers.microsoft.com/api/pcsx/search?domain=microsoft.com&query=intern&location=&filter_employment_type=Internship. Resolution: treat Microsoft as a changing careers platform and implement the PCSX API now with a health check; do not revive the older gcsservices path unless live verification proves it again.
- Meta examples disagree on whether the GraphQL endpoint is no-auth and directly usable or native-direct requests fail with `400 Bad Request`; one scraper states “No auth required,” while another source says direct POST needs browser/session context and Playwright works — https://github.com/Myselfgitcone/job-hunter/blob/1229877a31e204437c3d4282e14711a0f30f23f8/backend/scrapers/meta_jobs.py vs https://github.com/ragesh28/ALL_CAREER/blob/c56e2ae6fd174d02a064ede164c38e241051843d/job_api_calls.md. Resolution: classify Meta as UNRESOLVED/high-risk until aplyx can extract a current `doc_id` and required request tokens from the live page in CI.
- Apple community adapters describe a POST JSON API at `jobs.apple.com/api/role/search`, while the official public HTML search page currently exposes usable rendered job listings even when direct API probing is unreliable from this environment — https://github.com/dipak-bhujbal/career-jump/blob/695f1c46acfad615e383168d06711378b9d70659/services/api/src/ats/custom/apple.ts vs https://jobs.apple.com/en-us/search?search=software%20engineer&location=united-states-USA. Resolution: implement Apple as HTML-first with API-probe fallback, not API-only.

## Resolved (2026-07-26, live verification — fetch_eightfold_listings.py replaced the Microsoft-only adapter)
- Microsoft's earlier "no JD-detail endpoint" conclusion (above) was wrong, not a platform limitation — it only ever tried one bad guess. The real endpoint is `/api/apply/v2/jobs/<id>?domain=<domain>`, confirmed live returning full `job_description` HTML for both Microsoft (`apply.careers.microsoft.com`) and Netflix (`explore.jobs.netflix.net`) — no Playwright fallback needed after all.
- Eightfold (the platform Microsoft's careers site runs on) also powers Netflix's careers site under a completely different custom domain, confirmed live — no common hostname suffix across tenants (unlike Oracle/Workday, which share `.oraclecloud.com`/`myworkdayjobs.com`). Two different search endpoints exist on the platform (`/api/pcsx/search` and `/api/apply/v2/jobs`) and which one a given tenant accepts is per-tenant, not constant — Microsoft only accepts PCSX ("Not authorized for PCSX" on the generic endpoint), Netflix only accepts the generic one ("PCSX is not enabled for this user" on PCSX).
- Google's careers page (`google.com/about/careers/applications/jobs/results/`) DOES expose real, parseable data — a positional (unlabeled) array inside a server-rendered `AF_initDataCallback({key: 'ds:1', ...})` block, confirmed live. Richer than expected: full JD text (description + responsibilities + qualifications) is embedded directly in the list response, no separate detail fetch needed. Pagination is a plain `?page=<n>` param; `?q=<query>` filters. A working, non-auth-gated posting URL can be constructed as `.../jobs/results/<id>` (the ID alone resolves correctly; an exact slug isn't required). Implemented in `fetch_google_listings.py`, gated behind a structural health check given the format has no field names to key off.
- Gem (jobs.gem.com) is **not viable as a public/unauthenticated adapter** — investigated in full: found the real GraphQL endpoint (`https://jobs.gem.com/api/graphql`, discovered via the SPA's own bundled JS — `ExternalJobBoardList.*.min.js` contains the exact `JobBoardList($boardId: String!)` query used for listings, `jobBoards.*.min.js` contains the per-posting `ExternalJobPostingQuery`) and the real query shape for both list and detail. The endpoint returns `403 forbidden` on every attempt — correct headers (Origin/Referer matching the real site), and even a session cookie established via a real prior page load, made no difference. The CSP headers reference hCaptcha prominently, suggesting bot/WAF protection rather than a simple missing-header issue. Unlike Greenhouse/Lever/Ashby/Oracle/Workday/Eightfold, which are all genuinely open public APIs, this one is actively gated — implementing an adapter would mean working around that protection, which is out of scope.

## Recommendation
Implement in this order: (1) Microsoft PCSX/Eightfold list ingestion, because it covers a top employer with a clean current JSON search API; (2) a tenant-discovery pass for Oracle Recruiting Cloud and Workday so American Express, Salesforce, Nvidia, JPMorgan-like ORC tenants, and other large enterprises become config additions rather than custom scrapers; (3) Apple and Stripe HTML adapters, because both expose first-party rendered job lists without browser state; (4) Greenhouse/Lever/Ashby branded-page discovery improvements for Datadog, Palantir, OpenAI, and similar companies; (5) only then consider Google and Meta, and gate them behind health checks because their formats are more likely to break. This recommendation rests on the findings that Microsoft PCSX, Oracle HCM, Workday CXS, Greenhouse, Lever, Ashby, Apple HTML, and Stripe HTML all expose deterministic named or rendered data, while Meta and Google require undocumented frontend formats or browser-context extraction.

Weakest assumption: Microsoft’s `api/pcsx/search` endpoint will remain publicly accessible and sufficiently complete for list ingestion; if it disappears or lacks JD detail in practice, the priority should shift to Apple/Stripe plus Oracle/Workday tenant expansion.
